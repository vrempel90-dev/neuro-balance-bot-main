## Путь сообщения

`live_main:app` использует приложение main и post-processing observer. Webhook проходит аутентификацию и нормализацию, durable inbox сохраняет входящее до ACK. Worker обрабатывает очередь с FIFO одного чата и отдельной блокировкой чата. `main.handle_incoming_message` проверяет ночное окно и ручной режим; `dialog.handle_message` получает историю/сессию, проверяет новый лид через CRM; `agent.run_agent_turn` ведёт цикл model/tool. Python инструменты сохраняют факты, получают CRM врачей/время, создают запись с claims и проверкой readback. Финальный guard проверяет утверждения и язык; outgoing claim предотвращает повторную отправку.

Проверены agent, ai, dialog, services, bot_tools, admission, clinic_info, guards, strict_prompt_guard, language_guard, crm, state, main, live_main, production_inbox, production_monitor, production_webhook_auth, ai_budget, schedule, wazzup, repair observer и workflow CI/мониторинга. Два независимых read-only проверяющих исследовали медицинскую воронку и интеграции.

## Противоречия и решения в рамках текущего задания

- Primary §7 и новое ТЗ требуют хранить все сообщённые факты; старые profile-тесты требуют выбрасывать возраст до PROFILE. Исправляется тестовое ожидание в пользу явно утверждённого требования; gate остаётся закрыт.
- Primary исключает изолированную пятку, старый тест разрешает смешанную пятку/колено. Новое ТЗ требует не игнорировать ни одну жалобу. Консервативное техническое решение: при одновременно активных профильной и непрофильной жалобах UNCLEAR + один вопрос о цели консультации, без расширения медицинского профиля.
- Primary §12 допускает завершение текущей NEW-воронки после появления карточки. Текущий dialog отвергает любой последующий isNew=false. Нельзя разрешать исключение по локальному timestamp: только проверяемое происхождение того же lead, тот же телефон, новый статус, отсутствие patient/history/active appointment/staff takeover. Если этих доказательств нет, fail closed. Это ограничение CRM-контракта, а не разрешение игнорировать существующего пациента.
- Запись родственника разрешена по медицинскому профилю, но CRM-проверка сейчас привязана к отправителю. До предоставления CRM способа однозначно проверить пациента родственники требуют ручной проверки. Дополнительные медицинские направления/правила не вводятся.

## Надёжность, безопасность и ограничения доказательств

- Inbox сохраняет до ACK, выполняет same-chat FIFO и quarantine неопределённых операций; исходящие claims сохраняются до отправки. Нет оснований очищать реальные очереди.
- Booking success требует положительного результата CRM и readback. Ошибки CRMResponseError разделяются по HTTP/явному отказу; неизвестный результат должен удерживать блокировку пациента.
- Webhook token/OIDC/admin routes, media allowlist и редактирование логов покрыты существующими тестами; отсутствие дополнительного дефекта не означает абсолютную безопасность.
- SQLite/Volume путь, реальное состояние очередей и бизнес-качество текущей модели не доказаны одним статусом Railway Online. До релиза нужны read-only authenticated monitor и ручная сверка неизвестных операций.
- AI-budget проверяет перед вызовами и учитывает usage; денежный счётчик — оценка по локальной таблице тарифов, не биллинг OpenAI. Значения production и ограничения live API фиксируются отдельно, модель/переменные не меняются.
- Базовая Windows-среда: сначала 3 collection errors (нет tzdata); после установки tzdata только в venv — 605 passed/170 setup errors из-за недоступного системного pytest temp. Повторный чистый baseline использует workspace `--basetemp`; результаты будут в TEST_REPORT. Это не новые регрессии кода.
- `quality-gates.json` и `scripts/quality_gate.py` отсутствуют. Реальные CI gates: compileall, полный pytest и pip-audit requirements. UI/browser flow отсутствует; production path проверяется webhook/API и многоходовыми mocked диалогами.
